## Conventions

- **Match surrounding code.** Keep comment density, naming, and idioms consistent. Comments explain *why*; many files have a header comment worth reading before you edit.
- **No new infrastructure without asking.** Don't add services, runtimes, or tooling the project doesn't already use. Extend the existing build, container, and task-runner files rather than adding per-directory tooling.
- **Permissions.** Don't loosen an access rule as a side effect of other work; if a change touches who can do what, call it out.
- **Tests.** Add or extend automated tests for every change: request or integration tests for endpoints, unit tests for pure logic. For UI changes, verify in a real browser at desktop and mobile widths, and check both screenshots and the console for errors. Throwaway verification scripts go in a temp directory and aren't committed.
- **Git.** Commit only when asked. Don't push the production branch unless the user asks. Keep commit messages descriptive and in the style of `git log`.
- **Branches merge by rebase.** A rebase merge is always the preferred way to merge a branch or pull request. Before merging, rebase the branch onto the latest `origin/main` and rerun the checks; then merge it as a rebase merge (fast-forward main, or the code host's "Rebase and merge"), so main's history stays linear. When you enable auto-merge or suggest how to merge a pull request, pick rebase. Don't use merge commits or squash merges unless the user asks. Pushing a rebased branch you own needs `git push --force-with-lease`; never force-push main or a branch someone else is working on.
- **Delete merged branches.** Once a branch's merge is on `origin/main`, delete it on `origin` (`git push origin --delete <branch>`, or the code host's delete-branch option) and locally (`git branch -d <branch>`). Only delete a branch whose work is fully on main; never main itself, an unmerged branch, or one another session is still using. If the delete is refused, leave the branch and mention it.
- **Finishing a code change.** After a request that changes code, run `make test` (or the project's test command), then suggest one or more commit messages and ask the user to type "commit". When they do, `git add`, `git commit` and `git push`. With [prototyping mode](prototyping-mode.md) on, run the tests and commit and push without waiting; in [backlog mode](backlog-mode.md), follow its branch rules.
- **Asking the user questions.** Ask one question per message and wait for its answer before asking the next, even when one task raises several. If a question goes unanswered, ask it again; never assume an answer, including your own recommendation.
- **Large or ambiguous work (outside backlog mode).** Propose a scoped first step and confirm it with the user before building.
- **Other sessions work here too.** Several agents may work in a repo at once, so the working tree and `origin` can change under you. `git fetch` before assuming state, and check `docs/backlog/` and recent `git log` before a non-trivial build, since another session may have built it already. A rejected push because `origin` moved is routine: fetch, confirm the new commits don't touch your change, `git pull --rebase`, and push again. Never force-push a shared branch.
- **Production data.** Anything that writes or deletes production data (backfills, dedupes, resets) is dry-run first, and needs a backup and the user's go-ahead.
- **Project facts.** The project's stack, commands, roles and tooling are described in its `docs/project/`; they are facts to work with, not exceptions to these rules.
